## A moving recovery window

Suppose you set backup retention to seven days. As RDS keeps new recovery points available, older ones age out. A time you could restore to today may fall outside the window tomorrow, even though you haven't changed the setting.

To make that recovery possible, RDS takes automated snapshots during your configured backup window and uploads transaction logs. Together, they let you restore a **new DB instance** to an available time within the window. Manual snapshots have a separate lifecycle: they stay until you delete them. [AWS backup model ↗](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html)

## What RDS keeps

A point-in-time restore needs two kinds of backup data. The system snapshot supplies a storage baseline, and the transaction logs carry the database forward from that baseline to the time you choose.

For DB instances, RDS uploads transaction logs to Amazon S3 every five minutes. That cadence means the **latest restorable time** usually trails the present. Read the value reported by RDS instead of calculating it from the clock. When you restore, RDS creates another DB instance; it does not rewind the source instance in place. [AWS point-in-time restore ↗](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html)

## How the EBS delta snapshot works

RDS DB instances store database and log data on Amazon EBS volumes. The first automated snapshot captures the data for the full database. Later snapshots are incremental: EBS stores new copies of blocks that changed and continues referencing unchanged blocks it already holds. Although a later snapshot adds only the delta, it still represents a complete volume that EBS can restore. [RDS storage ↗](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/CHAP_Storage.html) [RDS snapshot behavior ↗](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html) [EBS block behavior ↗](https://docs.aws.amazon.com/ebs/latest/userguide/how_snapshots_work.html)

<IncrementalSnapshotModel />

When an earlier EBS snapshot is deleted, EBS removes only the data that no remaining snapshot needs. If a later snapshot still references an older block, EBS preserves that block and associates it with the later snapshot. An old restore point can therefore expire without breaking the restore points that follow it. [EBS snapshot deletion ↗](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-deleting-snapshot.html)

## Keep the four backup types separate

The RDS console places several backup choices close together, but they do not share one lifecycle. The distinction matters most when a recovery point must survive beyond the automated window or after you delete the source instance.

  <article>

  <article>
    <span class="type-label final">At deletion</span>

    <p>You can ask RDS to create this snapshot while deleting the instance. RDS then keeps it as a manual snapshot until you delete it.</p>
  </article>
  <article>
    <span class="type-label retained">Retained set</span>
    <h3>Retained automated backups</h3>
    <p>You can keep the existing system snapshots and transaction logs after deleting the instance. Their original retention period continues to age them out.</p>

## What expires—and what does not

As the automated window advances, RDS retires recovery points that fall outside it and removes backup data that the remaining range no longer needs. To find the boundary that matters, check the **earliest restorable time** reported for the instance. Counting visible snapshots does not tell you the available point-in-time recovery range.

## Deleting the instance

When you delete a DB instance, RDS asks two separate questions. One controls whether RDS creates a new final snapshot. The other controls whether it temporarily keeps the automated recovery data that already exists.

<div class="decision-tree" aria-label="Backup choices when deleting an RDS DB instance">
  <div class="decision-root">Delete DB instance</div>
  <div class="decision-branch">
    <article>
      <span>Choice A</span>
      <h3>Create a final snapshot?</h3>
      <p><strong>Yes:</strong> RDS creates a manual snapshot that stays until you delete it.</p>
      <p><strong>No:</strong> RDS does not create a new snapshot during deletion.</p>
    </article>
    <article>
      <span>Choice B</span>
      <h3>Retain automated backups?</h3>
      <p><strong>Yes:</strong> RDS keeps the existing recovery set while its original retention window runs out.</p>
      <p><strong>No:</strong> RDS deletes the same-Region automated backups with the instance.</p>
    </article>
  </div>
</div>

Deleting the instance does not delete manual snapshots that already exist. A final snapshot is also independent of retained automated backups. AWS recommends creating one even if you retain the automated backups, because the retained recovery window eventually expires. [AWS deletion behavior ↗](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_DeleteInstance.html)

## Limits that change the answer

The seven-day example explains the movement, but these service rules determine what RDS can actually retain and restore.

<div class="fact-stack">
  <div><strong>1–35 days</strong><span>You can configure this automated-backup retention range for an RDS DB instance. A value of 0 disables automated backups.</span></div>
  <div><strong>Every 5 minutes</strong><span>RDS uploads transaction logs for DB instances at this documented cadence. The latest restorable time can still trail the present.</span></div>
  <div><strong>New instance</strong><span>Both snapshot restores and point-in-time restores create another DB instance. They do not replace the source.</span></div>
  <div><strong>Available state</strong><span>RDS takes automated backups while the instance is available. States such as <code>storage_full</code> prevent them.</span></div>
</div>

RDS pauses the retention clock while a DB instance is stopped. Multi-AZ DB clusters cannot set retention to 0, and retained automated backups have additional limits after deletion. Aurora uses a different continuous-backup model, so the behavior on this page applies to RDS DB instances.

## Cost without false precision

RDS counts automated backups and manual DB snapshots toward backup storage in a Region. The allowance and resulting charges depend on your running database storage and the current RDS pricing rules. After you delete the source instance, retained automated backups and manual snapshots may continue to incur charges.

Retention tells RDS how long to maintain recoverability; it does not create a fixed number of fully billed copies. Storage use and cost also depend on how much data changes, which manual snapshots or copies you keep, the Region, and whether the source database still exists. Check the RDS billing metrics and current pricing before making a cost decision.
