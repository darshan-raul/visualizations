## The mental model

An RDS backup retention period is a **moving recovery window**. RDS creates automated storage snapshots during the configured backup window and uploads database transaction logs. Together, those backups let RDS restore a **new DB instance** to a point inside the available recovery window. [AWS backup model ↗](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html)

It is tempting to picture retention as seven independent, permanent copies when the setting is seven days. That model creates the wrong intuition. Automated backups age out as the window advances; manual snapshots follow a different lifecycle.

For DB instances, RDS uploads transaction logs to Amazon S3 every five minutes. The **latest restorable time** therefore trails the present; it should be read from RDS rather than calculated locally. A point-in-time restore does not rewind the running database in place—it creates another DB instance. [AWS point-in-time restore ↗](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html)

## How the EBS delta snapshot works

RDS DB instances use Amazon EBS volumes for database and log storage. The first automated snapshot contains the data for the full database; subsequent snapshots are incremental and save only data changed since the most recent snapshot. At the EBS layer, that means changed or new blocks are stored again while unchanged blocks already present in the snapshot lineage are referenced. Each snapshot still represents a complete restorable volume state. [RDS storage ↗](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/CHAP_Storage.html) [RDS snapshot behavior ↗](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html) [EBS block behavior ↗](https://docs.aws.amazon.com/ebs/latest/userguide/how_snapshots_work.html)

<IncrementalSnapshotModel />

When an earlier EBS snapshot is deleted, only data referenced exclusively by that snapshot is removed. Older blocks that a later snapshot still needs are preserved and associated with the later snapshot, so deleting the base does not break newer restore points. This is why an expiring snapshot does **not** imply that all blocks first captured with it disappear. [EBS snapshot deletion ↗](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-deleting-snapshot.html)

> **Boundary of the model:** AWS documents both RDS incrementality and EBS block-reference behavior, but RDS does not expose its managed backup graph or cleanup schedule. The diagram explains the storage semantics; it is not a literal view of an internal RDS chain that you can inspect or manage.

## What expires—and what does not

When an automated recovery point moves outside the retention window, RDS removes what is no longer required to offer that recovery range. The operational fact to rely on is the **earliest restorable time**, not the presence of a particular daily snapshot.

## Deleting the instance

Deletion presents two independent backup choices. Treat them separately.

<div class="decision-tree" aria-label="Backup choices when deleting an RDS DB instance">
  <div class="decision-root">Delete DB instance</div>
  <div class="decision-branch">
    <article>
      <span>Choice A</span>
      <h3>Create a final snapshot?</h3>
      <p><strong>Yes:</strong> a persistent snapshot remains until you delete it.</p>
      <p><strong>No:</strong> no new final snapshot is created.</p>
    </article>
    <article>
      <span>Choice B</span>
      <h3>Retain automated backups?</h3>
      <p><strong>Yes:</strong> the existing recovery set remains temporarily and continues aging out.</p>
      <p><strong>No:</strong> same-Region automated backups are deleted with the instance.</p>
    </article>
  </div>
</div>

Manual snapshots that already exist are not deleted with the DB instance. A final snapshot is independent of retained automated backups, and AWS recommends taking one even when automated backups are retained because the retained set eventually expires. [AWS deletion behavior ↗](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_DeleteInstance.html)

## Operational boundaries

<div class="fact-stack">
  <div><strong>1–35 days</strong><span>Configurable automated-backup retention for an RDS DB instance. Setting it to 0 disables automated backups.</span></div>
  <div><strong>Every 5 minutes</strong><span>Documented transaction-log upload cadence for DB instances; this is not a promise that “now” is immediately restorable.</span></div>
  <div><strong>New instance</strong><span>Snapshot and point-in-time restores create a new DB instance rather than mutating the source in place.</span></div>
  <div><strong>Available state</strong><span>Automated backups occur while the DB instance is available, not in states such as <code>storage_full</code>.</span></div>
</div>

Time spent while an RDS DB instance is stopped is not counted toward its backup retention period. Multi-AZ DB clusters cannot set retention to 0, and retained automated backups after deletion have additional limitations. Aurora uses a different continuous-backup model and is outside this explainer’s scope.

## Cost without false precision

RDS backup storage in a Region includes automated backups and manual DB snapshots. Backup-storage allowances and charges depend on the running database storage and current RDS pricing. Retained automated backups and manual snapshots can incur charges after the source instance is deleted.

The safe mental model is: **retention controls recoverability, not a fixed number of full billed copies**. Change rate, manual snapshots, retained backups, copies, Region, and whether the source database still exists all affect storage usage or billing. Use RDS billing metrics and the current pricing page for an actual cost decision.

## Practical checklist

<div class="checklist">
  <div><span>01</span><p>Set retention from the recovery objective, not from a guess about snapshot count.</p></div>
  <div><span>02</span><p>Monitor the earliest and latest restorable times that RDS reports.</p></div>
  <div><span>03</span><p>Create a manual snapshot for a restore point that must outlive the rolling window.</p></div>
  <div><span>04</span><p>Before deletion, decide independently whether you need a final snapshot and retained automated backups.</p></div>
  <div><span>05</span><p>Test restoration into a new instance; backup existence alone does not prove recovery readiness.</p></div>
