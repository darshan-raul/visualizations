Your deployment calls `s3:PutObject`, but S3 returns `AccessDenied`. The useful starting point is the request itself: **which principal signed it, which action did it ask for, which resource did it name, and which context values travelled with it?**

This page keeps one request in view as it moves through IAM:

`arn:aws:sts::111122223333:assumed-role/AppDeployer/darshan` → `s3:PutObject` → `arn:aws:s3:::prod-artifacts/releases/app.zip`

AWS builds request context, finds every policy that applies, looks for a sufficient grant, applies the relevant limits, and lets any applicable explicit deny win. The diagrams organize documented policy relationships so you can reason about them; they do not represent AWS’s internal implementation order.

## Principal: who signed the request?

A principal is the entity AWS authorizes for this request. A person or workload may begin the journey, but temporary credentials often mean that an assumed-role session becomes the runtime principal that calls S3. That distinction affects which policies and condition keys match. [Principal forms ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_principal.html)

<PrincipalExplorer />

## Policies: where can permission come from?

Authentication establishes who is calling. Authorization comes from policy statements that match the action, resource, principal where required, and condition context. Identity and resource policies can supply permissions; other policy types cap those permissions or govern a specific access path. [IAM policy types ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies.html)

<PolicyExplorer />

AWS services differ in which resources and policy elements they support. A pattern that works for an S3 bucket policy may not transfer unchanged to a KMS key policy or another service.

## Evaluation: why was it allowed or denied?

The durable rules are straightforward: a request begins implicitly denied, it needs a relevant allow, limiting policies must permit the request when they apply, and an explicit deny overrides an allow. The details depend on the principal, accounts, resource-policy support, and the exact kind of principal named by a resource policy. [Evaluation logic ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic.html)

### Role and session principals are different

<PrincipalGrantComparison />

When a same-account resource policy grants directly to an assumed-role **session ARN**, permissions-boundary and session-policy implicit denies do not limit that direct grant. An applicable explicit deny still wins. A grant to the IAM **role ARN** remains limited by the role’s boundary and session policy. AWS recommends using role principals where possible. [Detailed allow and deny evaluation ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html)

## Guardrails: how is power capped?

Permissions boundaries help a platform team delegate role creation without allowing each new role to exceed an approved maximum. SCPs define a maximum for principals in member accounts as policy inheritance moves from the organization root through OUs to an account. RCPs provide the resource-side Organizations control for supported services.

<GuardrailExplorer />

Region guardrails need care because some AWS services use global endpoints or do not operate in an ordinary regional request path. A production policy should include the appropriate global-service exceptions rather than treating the diagram’s “approved Regions” label as a complete SCP.

## Sessions: what happens when a role is assumed?

An IAM role stores trust and permissions configuration. When an authorized caller invokes `AssumeRole`, AWS STS creates a named role session and returns an access key ID, secret access key, session token, and expiration. Those credentials represent the session until they expire. [Temporary credentials ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_temp.html)

<StsSequence />

`AssumeRoleWithSAML` and `AssumeRoleWithWebIdentity` change how the caller proves its identity to STS. `GetFederationToken` creates a federated-user session for older custom-broker patterns. The separate [Identity and Credential Flows](/aws-identity-credential-flows) page follows those credential artifacts in more depth.

## Cross-account: which two sides must agree?

Cross-account access is not synonymous with assuming a role. A caller can assume a role in the target account, or supported resources can grant the original external principal direct access. Both patterns require the appropriate caller-side and target-side authorization, but they produce different runtime principals. [Cross-account evaluation ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic-cross-account.html)

## Least privilege: how do you refine access?

Least privilege is easier to maintain when you treat a policy as an evidence-backed draft. Start with the task, validate the syntax and service support, test the actual request, observe use, and remove permissions that the principal does not need.

<LeastPrivilegeLoop />

Prefer federation and temporary role credentials for people and workloads. Use strong identity-provider controls for privileged humans, separate everyday and elevated roles, govern tags before relying on ABAC, review external trust, and log sensitive policy changes and unusual role assumptions.

## Diagnose an AccessDenied

Start with the failed request rather than reading every policy in the account. An AWS error can identify one reason for denial without listing every reason, so work outward from evidence.

Policy Simulator and IAM Access Analyzer can narrow the investigation, but confirm their findings against the service’s authorization model and the actual request context. Broader administrator access cannot overcome an explicit deny.
