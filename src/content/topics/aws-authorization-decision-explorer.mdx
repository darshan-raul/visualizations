## Start with the request

Suppose the AWS CLI returns `AccessDenied` for one S3 request. Knowing that the caller is an administrator is not enough to explain the result. AWS evaluates the **principal** that signed this request, the requested **action**, the target **resource**, and the available **condition** values—the PARC model. Network origin, organization membership, session tags, resource tags, time, MFA context, and service-specific values can all affect that request. [AWS request context ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-reqcontext.html)

## Three rules, then the exceptions

The durable starting rules are:

1. A request is implicitly denied unless the applicable policy model supplies the required allow.
2. Any applicable explicit `Deny` wins over an `Allow`.
3. Limiting policies—permissions boundaries, session policies, SCPs, and RCPs—do not independently grant permissions.

These rules get you started, but they do not settle every request. Within one account, identity- and resource-based permissions commonly contribute allows, while permissions boundaries and Organizations policies limit what those allows can authorize. Account boundaries, service behavior, principal type, the principal named in a resource policy, and the applicable Organizations policies all change the final evaluation. [Policy evaluation overview ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic.html)

A simple policy diagram can orient you, but it cannot replace the request details. Identify the accounts, principal type, and applicable policies before deciding where an allow or deny comes from.

AWS services do not all support the same resource-policy model or policy elements. IAM role trust policies and AWS KMS key policies also have special requirements. Check the authorization documentation for the service that received the request before transferring a rule from another service.

## Same-account and cross-account

For many same-account requests, either an identity policy or a resource policy can provide the allow, as long as no explicit deny or limiting policy blocks it. A cross-account request normally needs authorization on both sides: the principal's account permits the request, and the resource's account trusts that principal through a resource policy. [Cross-account evaluation ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic-cross-account.html)

Assuming a cross-account role is one example of this handshake. The caller’s identity policy permits `sts:AssumeRole` on the target role, while the target role’s trust policy accepts the caller. Afterward, service requests made with the new credentials are evaluated as requests by the target role session. Do not mix the authorization decision that **creates the session** with the later decision that **authorizes an S3, EC2, or other service action**.

## The role-session principal edge case

<PrincipalGrantComparison />

When a same-account resource policy grants directly to an assumed-role **session ARN**, AWS grants to that session principal. An implicit deny in an identity policy, permissions boundary, or session policy does not limit that direct grant. An applicable explicit deny still wins. By contrast, a resource-policy grant to an IAM **role ARN** is limited by implicit denies in its permissions boundary or session policy. [Detailed allow/deny evaluation ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html)

AWS therefore recommends role principals where possible. Conditions using `aws:PrincipalArn` can often express role-level restrictions, but evaluate them with the surrounding principal, effect, account boundary, and policy type. [Principal element guidance ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_principal.html)

## Conditions are part of the match

<PolicyStatementMatch />

A statement matches only when its conditions match too. Condition keys can describe the principal, organization, network path, source resource, tags, authentication state, or request parameters. Before broadening a policy, check the operator and confirm that the request actually contains the key the condition expects.

## Diagnose an AccessDenied

Start with the failed request rather than reading every policy in the account.

  ['5. Check limiters', 'Do the boundary, session policy, SCP, or RCP permit the request?', 'Applicable policies at the identity, session, account, OU and organization levels'],
  ['6. Search explicit denies', 'Does any applicable statement deny this request?', 'Identity, resource, endpoint, key, Organizations, and service-specific policies'],

An error message can identify one reason for denial without enumerating every reason. Policy simulation and Access Analyzer can help, but neither replaces checking service-specific authorization behavior and the actual request context. Change the narrowest incorrect policy or context assumption; attaching a broader administrator policy will not overcome an explicit deny.
