## Start with AWS STS

AWS Security Token Service (STS) issues temporary AWS security credentials. It is the credential exchange in flows such as `AssumeRole`, SAML federation, and web-identity federation. STS does not attach permissions to a human and it does not permanently transform one identity into another. It evaluates a credential request and, when allowed, creates a time-limited session with a new credential set. [Temporary security credentials ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_temp.html)

The ordinary `AssumeRole` call is itself a signed AWS API request. Its caller must therefore already have usable AWS credentials. A person may initiate the command, but the AWS caller is the IAM user, federated session, or role session represented by those starting credentials. A workload follows the same rule: it signs `AssumeRole` with its current credentials.

**Authentication** establishes or validates who is making a request. **Credentials** are the material used to prove that identity to a system. A **role** is an IAM identity with trust and permissions configuration. A **role session** is the principal created when that role is assumed. Authorization then decides what that session may do.

## What AssumeRole creates

`AssumeRole` accepts an authenticated request for a target role and returns a distinct credential set: access key ID, secret access key, session token, and expiration. Temporary credentials must include the session token in subsequent requests and stop working after expiration. They do not mutate the caller’s credentials or turn the caller’s IAM object into the target role. [AssumeRole API ↗](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html) [Using temporary credentials ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_temp_use-resources.html)

An optional session policy can narrow the permissions granted by the role; it cannot expand them. A role’s maximum session duration can be configured from one to twelve hours, but an `AssumeRole` call made with role credentials—role chaining—is limited to one hour. [AssumeRole duration and session policies ↗](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html)

## Identity Center reaches role credentials differently

An IAM Identity Center profile separates the reusable SSO session configuration from the account-and-role selection. `aws sso login` obtains and caches an IAM Identity Center access token and refresh token. When a command needs AWS credentials, the SSO credential provider uses the selected account and role to request role credentials. The CLI can renew expired AWS credentials while the Identity Center session remains valid. [AWS CLI Identity Center concepts ↗](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sso-concepts.html)

```ini
[profile prod]
sso_session = company
sso_account_id = 222222222222
sso_role_name = ReadOnlyAccess
region = ap-south-1

[sso-session company]
sso_region = ap-south-1
sso_start_url = https://example.awsapps.com/start
sso_registration_scopes = sso:account:access
```

The authentication token is cached under `~/.aws/sso/cache`. Treat the cache and its JSON fields as tool-managed implementation details: do not edit them or build automation against their private layout. The profile contains no `aws_access_key_id` or `aws_secret_access_key`. [AWS CLI SSO configuration ↗](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sso.html)

Assigning a permission set to an account causes IAM Identity Center to create and manage a corresponding role whose name begins with `AWSReservedSSO_`. The permission set is the provisioning template; the role and its policies are the account-side IAM resources. Deleting and recreating all assignments can change the role’s unique ARN suffix, which matters when another resource policy refers to that ARN. [Identity Center-created roles ↗](https://docs.aws.amazon.com/singlesignon/latest/userguide/identity-center-and-iam-roles.html)

## The cross-account handshake

For a normal cross-account role assumption, account A grants its principal permission to call `sts:AssumeRole` on the role ARN, and the role trust policy in account B accepts that principal. Trusting an account delegates authority to that account; it does not automatically authorize every principal inside it. [Cross-account evaluation ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic-cross-account.html)

Once STS returns credentials, the application acts as a new session principal in account B. The target role’s permissions—not the caller’s previous permissions—form the base for what the new session can do. The application may still retain the old credential set separately, but one signed request uses one selected credential set.

## AssumeRole is not PassRole

`sts:AssumeRole` asks STS to return credentials to the caller. `iam:PassRole` is a permission checked when a caller configures an AWS service with a role ARN—for example, creating a Lambda function with an execution role. PassRole is not an API operation and returns no credentials. [AWS PassRole guide ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_use_passrole.html)

<AssumeRolePassRoleComparison />

Scope PassRole to approved role ARNs and, where supported, the destination service with `iam:PassedToService`. The service and passed role must be in the same account. To audit the association, inspect the CloudTrail event for the creating or updating service API, such as `CreateFunction`; there is no separate PassRole event.

## External ID binds a deputy to its customer

External ID addresses a specific cross-account confused-deputy problem: a multi-tenant provider is trusted to assume customer roles, and one customer tricks it into using another customer’s role ARN. A role ARN is not a secret. The protection comes from the vendor deriving the external ID from the authenticated tenant and the customer role requiring the matching value. [AWS confused-deputy guidance ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/confused-deputy.html)

```json
{
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::444444444444:role/VendorWorker" },
  "Action": "sts:AssumeRole",
  "Condition": {
    "StringEquals": { "sts:ExternalId": "darshan-789" }
  }
}
```

The vendor—not the customer—should generate and control a unique external ID for each customer. External ID is not authentication for the vendor, not encryption, not a general-purpose secret, and not a substitute for scoping the trusted principal and the role’s permissions.

## Role ARN and session ARN

The IAM role ARN identifies persistent configuration. The STS assumed-role ARN identifies one class of session principals created from it:

```text
arn:aws:iam::222222222222:role/AppSupportRole
                         │
                         │ AssumeRole
                         ▼
arn:aws:sts::222222222222:assumed-role/AppSupportRole/darshan
```

Policies sometimes expose a surprising difference between granting to the role ARN and granting directly to a role-session ARN. AWS recommends granting to role principals where possible and using conditions when further scoping is needed. Directly naming sessions is brittle because session names vary, and same-account resource-policy grants to a session principal interact differently with implicit denies from boundaries and session policies. [Role session principals ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_principal.html)

## Session context and auditability

The role session name appears in the assumed-role ARN and CloudTrail data. `SourceIdentity` can preserve an originating identity in session context and across subsequent role assumptions when configured. Session tags can carry attributes for attribute-based access control; tags marked transitive can persist through role chaining. These controls improve attribution and authorization context, but they require trust-policy permissions and constraints so callers cannot supply untrusted values freely. [Source identity ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_temp_control-access_monitor.html) [Session tags ↗](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_session-tags.html)
