## The mental model

A VPC connection works when **the destination can be reached, the traffic is permitted, and the reply can get back**. A route chooses a path. A security rule permits traffic on that path. Address translation can change what the next component sees. These are separate decisions.

An elastic network interface (ENI) is a resource’s network interface. A subnet supplies its address range; a subnet route table tells the VPC’s implicit router where to direct traffic. The route with the longest matching destination prefix normally wins. A route to a gateway leaves the packet’s destination address intact unless a translation function changes it. [AWS routing ↗](https://docs.aws.amazon.com/vpc/latest/userguide/subnet-route-tables.html)

## Routes choose where, rules choose whether

Consider the following subnet route table. A packet for `10.1.2.10` matches both `10.1.0.0/16` and `0.0.0.0/0`; the more specific `/16` selects peering. Rules that break ties between equally specific routes depend on their type. **Route selection is not a firewall decision.** [AWS route priority ↗](https://docs.aws.amazon.com/vpc/latest/userguide/route-tables-priority.html)

A subnet is public when its route table has a direct route to an internet gateway. For ordinary direct IPv4 internet access, an EC2 instance also needs a public address or Elastic IP and suitable filtering. Adding an IGW route to an instance with only a private IPv4 address is insufficient. [IGW requirements ↗](https://docs.aws.amazon.com/vpc/latest/userguide/VPC_Internet_Gateway.html)

## Addresses and translation

In the public EC2 trace, the internet client addresses `203.0.113.10:443`, while the instance receives traffic for `10.0.1.5:443`. The IGW supplies the public/private IPv4 mapping; the guest does not configure that public address on its interface. The reverse mapping restores the public source on the reply. [IGW translation ↗](https://docs.aws.amazon.com/vpc/latest/userguide/VPC_Internet_Gateway.html)

The NAT trace makes two translations visible: the gateway maps the client to its own private address and a source port, then the IGW maps that private address to the NAT Elastic IP. The reply reverses those mappings. The illustrated port `62000` is an example, not a predicted allocation. Unsolicited inbound internet connections cannot use this existing outbound-only design. [NAT behavior ↗](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-nat-gateway.html)

The explorer deliberately uses a **zonal** NAT gateway. Regional NAT gateways have a different placement and routing model, with an AWS-managed route table rather than requiring a user-selected public subnet. Do not apply the zonal placement rule to every NAT gateway type. [Regional NAT ↗](https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateways-regional.html)

IPv6 routes are separate from IPv4 routes: `0.0.0.0/0` does not cover `::/0`. An egress-only internet gateway supplies outbound-only IPv6 connectivity without translating IPv6 into IPv4; DNS64/NAT64 is a different mechanism for IPv6 clients accessing IPv4 destinations. [IPv6 egress ↗](https://docs.aws.amazon.com/vpc/latest/userguide/egress-only-internet-gateway.html) [NAT64 ↗](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-nat-gateway.html)

## Why the reply can fail

The strongest test is the **Internet → public EC2** scenario with a reply-side NACL failure. The request reaches the server on port 443; the reply goes to the client’s temporary port **52140**, not to destination port 443.

Security-group state allows replies to an admitted connection even if the reverse-direction SG rules would not independently admit a new connection. It does not create missing routes or override ACLs. The illustrated flow assumes normal connection tracking. [Security groups ↗](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-security-groups.html)

ACL rules evaluate destination ports in each direction. For a private client initiating HTTPS, the inbound reply rule must allow the client ephemeral port. For a public server accepting HTTPS, the **outbound** reply rule must allow the remote client ephemeral port. Real ephemeral ranges depend on the client or translating device; `1024–65535` is a broad compatibility range, not every operating system’s allocation range. [ACL rules ↗](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-network-acls.html) [Ephemeral ports ↗](https://docs.aws.amazon.com/vpc/latest/userguide/custom-network-acl.html)

## Peering and transit gateway route domains

Peering joins two non-overlapping VPC address spaces. Both participating subnet route tables need routes for the other side, and network rules must allow the flow. **A ↔ B and B ↔ C do not imply A ↔ C.** Peering is not transitive, and it does not let a peer borrow another VPC’s internet gateway or gateway endpoint. Cross-Region peering SG rules use CIDRs rather than references to the remote SG. [Peering boundaries ↗](https://docs.aws.amazon.com/vpc/latest/peering/vpc-peering-basics.html)

A transit gateway (TGW) is a routing hub. A VPC subnet first selects its TGW attachment. Then the TGW uses the table **associated with the attachment on which traffic arrived** to select the next attachment. Association chooses the lookup table; propagation installs reachable prefixes into chosen tables. These are distinct configuration choices. [TGW routing ↗](https://docs.aws.amazon.com/vpc/latest/tgw/how-transit-gateways-work.html)

<TransitGatewayRouteDomains />

For TGW peering, configure static routes to the peering attachment in both directions. The explorer shows four TGW lookups across the round trip, so a missing return lookup is visible. Stateful inspection adds a symmetry requirement; appliance mode on the inspection VPC attachment helps preserve the flow’s path, but the surrounding routes still need to be correct. [TGW peering ↗](https://docs.aws.amazon.com/vpc/latest/tgw/tgw-peering.html) [Appliance mode ↗](https://docs.aws.amazon.com/vpc/latest/tgw/how-transit-gateways-work.html)

## Cross-Region and hybrid boundaries

Crossing a Region does not imply a universal 1,500-byte MTU. AWS currently documents **8,500 bytes for inter-Region VPC peering**, and TGW supports 8,500 bytes across its peering attachments. The usable end-to-end MTU is constrained by the smallest link along the actual path; VPN encapsulation and other devices introduce their own limits. Small successful probes do not prove that larger packets will pass. [VPC peering MTU ↗](https://docs.aws.amazon.com/vpc/latest/peering/vpc-peering-basics.html) [TGW MTU ↗](https://docs.aws.amazon.com/vpc/latest/tgw/what-is-transit-gateway.html)

The hybrid sequences above are configuration paths: virtual interfaces, gateway associations and routing all need to agree. Direct Connect provides a dedicated connection, but does not encrypt traffic by default. Use appropriate TLS, supported MACsec, or an IPsec VPN design when encryption is required. MACsec protects its link; it is not a substitute for application-to-application encryption. [Direct Connect encryption ↗](https://docs.aws.amazon.com/directconnect/latest/UserGuide/encryption-in-transit.html)

Cloud WAN extends the routing-policy discussion to a managed global core and segments. It does not remove the need to reason about which segment can reach which destination and how the reply returns. [Cloud WAN overview ↗](https://docs.aws.amazon.com/network-manager/latest/cloudwan/what-is-cloudwan.html)

## Subnet details worth remembering

For a normal AWS-assigned IPv4 subnet `10.0.1.0/24`, AWS reserves the first four and last addresses: `.0`, `.1`, `.2`, `.3`, and `.255`, leaving 251 assignable addresses. The `.1` address is reserved for the VPC router; VPCs do not support broadcast. BYOIP has different address-allocation exceptions. [Subnet addressing ↗](https://docs.aws.amazon.com/vpc/latest/userguide/subnet-sizing.html)

The subnet’s reserved `.2` address does **not** mean a separate resolver lives at the base-plus-two address of every subnet. For a VPC with primary CIDR `10.0.0.0/16`, the Amazon DNS server address is `10.0.0.2`; AWS also provides the link-local resolver address `169.254.169.253`. [VPC DNS ↗](https://docs.aws.amazon.com/vpc/latest/userguide/AmazonDNS-concepts.html)

Availability Zone names may map differently between accounts. Use AZ IDs when you need to compare the same physical Availability Zone across accounts. An AZ can contain multiple data centers. [AZ IDs ↗](https://docs.aws.amazon.com/ram/latest/userguide/working-with-az-ids.html)
