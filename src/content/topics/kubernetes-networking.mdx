## Begin with one Pod

Imagine a web application that calls an API. Before connecting the two, look at where one application runs.

Kubernetes schedules containers in a **Pod**. A Pod can contain a single container or a few containers that need to run together. In an ordinary Pod, those containers share one network namespace—the Linux view of interfaces, addresses, routes, and ports. [Pod networking ↗](https://kubernetes.io/docs/concepts/workloads/pods/)

<ProgressiveNetwork stage="pod" />

**Keep this idea:** containers in one Pod share localhost. They must coordinate ports because they cannot independently listen on the same address and port. A different Pod has its own localhost.

## Reach another Pod

Now put the API in its own Pod. The web application must use the API Pod’s address; calling localhost would still reach only its own Pod.

<ProgressiveNetwork stage="pods" />

A **Node** is a machine running Pods. The cluster’s network implementation connects those Pods across Nodes. **CNI** is the interface through which the runtime invokes network plugins during Pod setup. You can understand the connection before learning which Linux interfaces implement it.

**Keep this idea:** different Pods communicate through Pod addresses. The app must be listening, and the network and security rules must permit the connection.

### How the Pod gets connected


All regular containers in a Pod share the Pod sandbox's network namespace, addresses, interfaces, routes, and port space. They communicate over `localhost`; two containers cannot independently bind the same address and port. The sandbox may be represented by an infrastructure container, but “the pause container owns networking” is an implementation shortcut, not the Kubernetes contract. [Pod networking ↗](https://kubernetes.io/docs/concepts/workloads/pods/)

<WorkflowDiagram id="k8s-cni-lifecycle" lanes={['Kubelet', 'Container runtime', 'CNI plugins', 'Pod sandbox']} steps={[
  ['Kubelet', 'Request the Pod sandbox', 'CRI RunPodSandbox', 'Kubelet asks the node runtime to prepare the Pod sandbox.'],
  ['Container runtime', 'Prepare network isolation', 'Network namespace', 'In this ordinary Linux Pod example, the namespace exists before network attachment.'],
  ['CNI plugins', 'Attach and configure networking', 'CNI ADD + optional IPAM delegation', 'The runtime supplies the namespace reference and configuration. Plugins configure networking and may delegate address allocation.'],
  ['Container runtime', 'Receive the plugin result', 'Interfaces, IPs, routes, DNS', 'The runtime receives the CNI result. Exact interfaces and forwarding mechanisms belong to the plugin implementation.'],
  ['Pod sandbox', 'Share the configured network', 'Pod IP + shared port space', 'Containers in this Pod use the sandbox network. This setup is not repeated for each packet.'],
]} />

CNI is an execution protocol between a runtime and plugin binaries. It defines operations such as `ADD`, `DEL`, `CHECK`, `GC`, `STATUS`, and `VERSION`; it does not mandate a bridge, an overlay, a particular IPAM database, or NetworkPolicy enforcement. Plugins can be chained, and an IPAM plugin can be delegated address allocation. [CNI specification ↗](https://www.cni.dev/docs/spec/)

When a Pod is deleted, the runtime invokes cleanup. A leaked IP allocation, stale interface, or failed plugin daemon can therefore break later Pod creation even when the Kubernetes objects look valid.


</section>


<NetworkDepth id="addresses-belong-to-different-planes" label="Compare Node, Pod, and Service addresses">

Nodes, Pods, and Services commonly draw addresses from separate, non-overlapping ranges. Different components allocate and route each range, so available addresses in one pool say nothing about capacity in another. A dual-stack cluster repeats these responsibilities for IPv4 and IPv6, and every participating component must support the configured families. [Cluster address ranges ↗](https://kubernetes.io/docs/concepts/cluster-administration/networking/)

`containerPort` documents an application port but does not publish it. `hostPort` binds a Pod port on a Node and creates scheduling/port constraints. `hostNetwork: true` places the Pod in the Node network namespace instead of the ordinary pod network. These are exceptions, not the default path.

## Give the API a stable address

Pods can be replaced, and replacement Pods can receive different addresses. A **Service** gives the web application a stable destination while the API Pods behind it change.

For the ordinary internal Service below, the web app first asks cluster DNS for the name `api`. DNS returns the Service’s virtual IP, called a **ClusterIP**. When the app connects, the Service’s forwarding implementation selects an eligible backend Pod.

<ProgressiveNetwork stage="service" />

The Service’s `port: 80` is what callers use; `targetPort: 8080` is where the API listens. **EndpointSlices** are the backend records the Service implementation consults. [Services ↗](https://kubernetes.io/docs/concepts/services-networking/service/)

**Keep this idea:** DNS finds the address; Service forwarding gets the connection to a backend. A successful name lookup does not prove that the API can answer.

<ServiceEndpointExplorer />

<NetworkDepth id="services-and-endpointslices" label="Inspect backend selection and compare all Service forms">

A Service separates a stable frontend from a changing backend set. For a selector-based Service, the control plane finds matching Pods and maintains EndpointSlices. Each slice groups endpoints with compatible address family, protocol, port, and Service identity. Readiness, serving, and terminating conditions help consumers decide whether an endpoint should receive new traffic. [Services ↗](https://kubernetes.io/docs/concepts/services-networking/service/) [EndpointSlices ↗](https://kubernetes.io/docs/concepts/services-networking/endpoint-slices/)



The legacy `Endpoints` API is deprecated from Kubernetes v1.33; EndpointSlice is the scalable source for modern consumers. The default slice target is up to 100 endpoints, but slices are not continually repacked just to be full because every update must propagate to consumers across the cluster.

Endpoint removal is also a convergence process rather than one instantaneous switch. The timeline below shows why readiness, published endpoint state, proxy state, and existing connections can briefly disagree while a Pod terminates.

<NetworkDepth id="the-service-data-plane" label="Under the hood: kube-proxy, forwarding rules, and existing connections">

`kube-proxy` is Kubernetes' default Service proxy, but a pod network implementation can replace it. On Linux, kube-proxy can program iptables or nftables; IPVS mode is deprecated from Kubernetes v1.35 because it cannot correctly represent every Service edge case. Windows uses a different kernel data plane. [Virtual IPs and proxies ↗](https://kubernetes.io/docs/reference/networking/virtual-ips/)

The word “proxy” is easy to misread: kube-proxy usually programs kernel forwarding rules rather than accepting every connection in a user-space process. A ClusterIP is similarly virtual—the Service API defines the frontend, while the chosen implementation decides how packets addressed to it are intercepted and redirected.

<ReferenceTable caption="Service proxy implementations" headers={['Mode', 'Mechanism', 'Operational implication']} rows={[
  ['iptables', 'Netfilter rules and destination NAT', 'Widely deployed; large rule sets can increase synchronization work.'],
  ['nftables', 'nftables rules and destination NAT', 'Newer Linux mode with different NodePort and firewall defaults; verify kernel and Kubernetes support.'],
  ['IPVS', 'IPVS plus iptables integration', 'Deprecated from v1.35; plan migrations instead of choosing it for new clusters.'],
  ['Replacement data plane', 'Implementation-specific, often eBPF or provider integrated', 'Do not expect kube-proxy processes or KUBE-* rules when it has been replaced.'],
]} />

Removing a Pod from EndpointSlices stops it from being selected for new traffic after consumers reconcile the update. Existing application connections and connection-tracking entries have their own lifetimes, so they can continue using that Pod after readiness changes.

</NetworkDepth>


<NetworkDepth id="dns-is-discovery-not-delivery" label="Inspect DNS names, resolver configuration, and discovery failures">

Cluster DNS commonly runs CoreDNS behind a Service historically named `kube-dns`. With the usual `ClusterFirst` policy, kubelet writes a cluster DNS nameserver and search suffixes into the Pod's resolver configuration. A query such as `api` can expand to `api.<namespace>.svc.<cluster-domain>`; cross-namespace callers normally use `api.<namespace>` or the full name. The cluster domain is configurable and is not always `cluster.local`. [DNS for Services and Pods ↗](https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/)

<MechanismFlow label="DNS discovery followed by Service delivery" steps={[
  { title: 'Application asks resolver', detail: 'Search paths and ndots influence which names are queried.' },
  { title: 'Cluster DNS answers', detail: 'A normal Service returns its ClusterIP; a headless Service can return endpoint addresses.', tone: 'purple' },
  { title: 'Application opens a connection', detail: 'The returned address becomes the packet destination.' },
  { title: 'Network delivers traffic', detail: 'Service proxying or direct pod routing handles the result.', tone: 'green' },
]} />

A correct DNS answer proves that the client discovered an address. The following connection can still time out because the Service has no ready endpoints, forwarding state is stale, policy blocks the packet, or the application is not listening. Likewise, a successful direct Pod-IP test has bypassed both DNS and the Service frontend.

`ClusterFirstWithHostNet` is the usual cluster-DNS choice for Pods using `hostNetwork`. `dnsPolicy: None` requires explicit `dnsConfig`. Search expansion can also amplify DNS traffic, so inspect the actual query name and the Pod's `/etc/resolv.conf` rather than assuming what the application asked.

</NetworkDepth>


## Choose how callers reach it

For our web app calling its API inside the cluster, start with **ClusterIP**. When callers are outside the cluster, choose the entry behavior they need.

<ReferenceTable caption="Choose from the caller’s need" headers={['What you need', 'Start here', 'Why']} rows={[
  ['Web app → API inside the cluster', 'ClusterIP Service', 'Stable internal access to changing Pods.'],
  ['External access to one TCP/UDP service', 'LoadBalancer Service', 'A supported implementation provisions a reachable load balancer.'],
  ['HTTP/HTTPS host or path routing', 'Gateway API or Ingress', 'A controller configures entry routing and, commonly, TLS.'],
]} />

A LoadBalancer Service needs a supporting controller or provider. Gateway and Ingress resources also need an implementation. Creating their configuration alone does not make the application reachable.

### Service types and where to use them

<NetworkDepth id="northsouth-traffic" label="Explore Gateway and Ingress configuration">

External traffic needs infrastructure that can receive packets and an API/controller combination that maps them toward Services or endpoints. A `LoadBalancer` Service handles a relatively direct exposure model. Ingress and Gateway API add protocol-aware routing, usually for HTTP and HTTPS.

Ingress is stable but frozen; the Kubernetes project recommends Gateway API for new capabilities. Creating an Ingress, Gateway, or Route object alone does not create a working data path—an implementation controller must accept it and report useful status. Gateway API separates `GatewayClass`, `Gateway`, and route resources such as `HTTPRoute`, allowing infrastructure owners, cluster operators, and application teams to control different layers. [Ingress ↗](https://kubernetes.io/docs/concepts/services-networking/ingress/) [Gateway API ↗](https://gateway-api.sigs.k8s.io/docs/introduction/)

<MechanismFlow label="A typical Gateway API north-south path" steps={[

  { title: 'HTTPRoute', detail: 'Matches host, path, headers, or other request attributes.' },
  { title: 'Service backend', detail: 'Targets a Service and ultimately eligible endpoints.', tone: 'green' },

Where TLS terminates, whether traffic reaches NodePorts or Pod addresses directly, which health checks run, and whether the original client address survives are implementation decisions. Read controller status and documentation instead of treating the conceptual arrows as guaranteed hops.

</NetworkDepth>


<NetworkDepth id="locality-source-ip-and-topology" label="Explore local endpoints and client source addresses">

Service routing can express strict constraints and softer preferences. `internalTrafficPolicy: Local` restricts internal Service traffic to node-local endpoints; on a node with none, the Service behaves as if it has no endpoints there. `externalTrafficPolicy: Local` can preserve client source addresses and avoid an extra node hop, but may reduce load distribution and requires entry traffic to land on nodes with local endpoints. [Internal traffic policy ↗](https://kubernetes.io/docs/concepts/services-networking/service-traffic-policy/) [Source IP ↗](https://kubernetes.io/docs/tutorials/services/source-ip/)

`trafficDistribution` expresses preferences such as same-zone or same-node routing in supported versions; it is not the same as the hard `Local` constraint. EndpointSlice topology and hints can guide the proxy, but implementations may fall back to cluster-wide endpoints when safeguards are not satisfied.

Always test the source address as observed by the application. Load balancers, node forwarding, proxies, and `externalTrafficPolicy` can change it, and NetworkPolicy `ipBlock` behavior can be affected by where address translation occurs.

## Decide who may connect

Our web app needs to call the API. Other workloads might not. **NetworkPolicy** lets you describe allowed Pod traffic when the installed network implementation supports enforcement.

Think about a connection from both ends: permission to leave the web Pod (**egress**) and permission to enter the API Pod (**ingress**).

<ProgressiveNetwork stage="policy" />

Pods begin non-isolated in each direction. Selecting them with policies can restrict that direction; applicable allow rules add together. When introducing default-deny egress, allow the DNS traffic and other dependencies your app requires. [NetworkPolicy ↗](https://kubernetes.io/docs/concepts/services-networking/network-policies/)

**Keep this idea:** a route makes a destination reachable; policy decides whether the connection is permitted. Application identity and authorization add another layer.

<NetworkPolicyExplorer />

<SecurityControlMap />

<NetworkDepth id="networkpolicy-changes-permission" label="Try policy examples and inspect the security controls">

By default, Pods are non-isolated for ingress and egress. A NetworkPolicy begins isolation only for the selected Pods and directions, and allowed traffic is the union of every applicable policy—policies are additive, not processed in order. For Pod A to initiate a connection to Pod B, A's egress policy and B's ingress policy must both allow it when each side is isolated. Reply traffic for an allowed connection is implicitly allowed. [NetworkPolicy ↗](https://kubernetes.io/docs/concepts/services-networking/network-policies/)

The API does nothing unless the installed network implementation enforces NetworkPolicy. The standard model is primarily Layer 3/4 and defines TCP, UDP, and optionally SCTP behavior; ICMP and other protocols can vary. It does not replace application authentication or authorization.





<div class="network-principles">
  <article><span>Default allow</span><h3>No selecting policy means no isolation</h3><p>Creating one policy for a different workload does not make the whole namespace default-deny.</p></article>

<NetworkDepth id="the-layers-behind-a-connection" label="See the complete system map">

When one Pod connects to another, Kubernetes API objects describe the intended addresses, backends, and policy, but they do not carry the packet. The container runtime, Pod network, Service implementation, DNS server, and entry controller each perform part of the work. Two failures can produce the same timeout even when they occur in different layers, so you need both the declared state and the packet path. [Kubernetes networking model ↗](https://kubernetes.io/docs/concepts/services-networking/)

For any connection, ask four questions: **Who owns the destination address? How did the client discover it? Which data plane forwards the packet? Which policy can allow or reject it?**

<KubernetesNetworkMap />

Kubernetes defines connectivity outcomes, while each cluster chooses how to produce them. Linux bridges, VXLAN, iptables, kube-proxy, and the packet paths shown here are implementation choices rather than universal Kubernetes internals.

<NetworkDepth id="diagnose-one-layer-at-a-time" label="Troubleshoot a connection with commands and evidence">

Start beside the application, prove the shortest path, and add one layer at a time. If the workload image has no diagnostic tools, use a disposable Pod or ephemeral container in a comparable policy and network context. Plugin and managed-service commands vary, but the order of evidence remains useful.

<div class="command-stack">
  <div><span>01</span><p><strong>Application:</strong> confirm readiness, listening address, and port. Inspect <code>kubectl get pod -o wide</code>, events, logs, and the process socket from inside the Pod.</p></div>
  <div><span>02</span><p><strong>Direct Pod path:</strong> connect to the destination Pod IP and target port from a relevant source Pod. Failure here bypasses Service and DNS and points toward the app, pod network, or policy.</p></div>
  <div><span>03</span><p><strong>Backend membership:</strong> run <code>kubectl get endpointslice -l kubernetes.io/service-name=&lt;service&gt; -o wide</code>. Check addresses, ports, readiness, and terminating state.</p></div>
  <div><span>04</span><p><strong>Service frontend:</strong> inspect <code>kubectl get svc &lt;service&gt; -o yaml</code>, then test the ClusterIP and Service port. Verify <code>port</code> versus <code>targetPort</code>.</p></div>
  <div><span>05</span><p><strong>Discovery:</strong> query the fully qualified Service name, inspect <code>/etc/resolv.conf</code>, and verify the <code>kube-dns</code> Service plus its EndpointSlices.</p></div>
  <div><span>06</span><p><strong>Permission:</strong> list every policy selecting the source and destination. Confirm the installed implementation enforces the API, then verify which addresses policy observes along paths that also perform NAT.</p></div>
  <div><span>07</span><p><strong>Node data plane:</strong> identify kube-proxy mode or its replacement before inspecting iptables, nftables, eBPF maps, routes, interfaces, conntrack, or plugin-agent logs.</p></div>
  <div><span>08</span><p><strong>External entry:</strong> inspect Service, Gateway, and Route status conditions, controller events/logs, load-balancer health, firewall rules, TLS, and external DNS.</p></div>
</div>

Packet capture points must match the suspected layer. An overlay can show an inner Pod packet on one interface and an outer node-to-node packet on another. A missing packet at the destination is not enough to tell whether routing, encapsulation, policy, or Service selection removed it.

</NetworkDepth>


<NetworkDepth id="where-the-common-shortcuts-break-down" label="Check common misconceptions">

<div class="misconception-grid">
  <article><span>Misconception</span><h3>“CNI means VXLAN and a cni0 bridge.”</h3><p>CNI is a runtime/plugin contract. Bridges and overlays are possible implementations, not requirements.</p></article>
  <article><span>Misconception</span><h3>“kubelet directly configures every Pod interface.”</h3><p>Kubelet asks the container runtime to create the sandbox; runtimes commonly invoke CNI plugins for networking.</p></article>
  <article><span>Misconception</span><h3>“A Service is a process listening on its ClusterIP.”</h3><p>The frontend is virtual. A programmed data plane redirects or routes traffic toward eligible endpoints.</p></article>
  <article><span>Misconception</span><h3>“CoreDNS load-balances normal Service traffic.”</h3><p>For a normal Service, DNS generally returns the stable ClusterIP. Endpoint choice happens in the Service data plane.</p></article>
  <article><span>Misconception</span><h3>“NetworkPolicies are ordered firewall rules.”</h3><p>Applicable allows are additive. Isolation and permission are evaluated independently for ingress and egress.</p></article>
  <article><span>Misconception</span><h3>“Ingress exposes traffic by itself.”</h3><p>Ingress is configuration. A compatible controller and its provisioned data plane must implement it.</p></article>
</div>
