## Meet the network identity

An Elastic Network Interface is where VPC networking becomes concrete. It has a subnet, addresses, security-group associations, attachment state, and an owner. Compute may come and go around it; those fields still describe the network identity packets use.

<EniIdentity />

> [!NOTE]
> **Do not configure an Elastic IP as a local guest address.** For public IPv4 traffic, the internet gateway maps the public address to the ENI's private IPv4. Also remember that “persistent” lasts only while the EIP remains allocated to you.

## Keep the subnet and Availability Zone boundary visible

An ENI is created in one subnet, and that subnet fixes its Availability Zone. Detaching the interface does not make it portable across zones. If a design crosses zones, draw a separate interface in each zone.

<EniTopology />

## Recognize the same primitive across services

EC2 exposes a customer-managed interface directly. Other services create requester-managed interfaces, manage attachments on your behalf, or abstract a shared data-plane interface. The subnet and address model remains useful, but the available controls change with ownership.

<EniServices />

> [!NOTE]
> **Requester-managed does not mean abandoned.** You can inspect these interfaces while the requesting service owns their lifecycle. Delete or change the parent service, not the interface underneath it.

## Put the interface on an appliance route

A firewall instance is not a router merely because two ENIs are attached. Route tables must send traffic to it, source/destination checking must permit transit traffic, and the guest OS must forward packets with a valid return path.

<EniOperations />

> [!NOTE]
> The failover example is deliberately same-AZ. An ENI cannot cross an Availability Zone, and moving one does not repair Linux routes, asymmetric return paths, or application state.

## Operate from the ENI outward

When a connection fails, identify the source and destination interfaces before opening every security rule. That gives you the correct subnet route table, security groups, NACL boundaries, ownership model, and Flow Log dimensions. For scaling failures, count network addresses and interface slots alongside CPU and memory.

The recurring question is simple: **where does this workload obtain its VPC network presence, and who controls that interface?** Answer that first, and many AWS networking diagrams collapse into a smaller set of concrete boundaries.
