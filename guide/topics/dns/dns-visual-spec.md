# DNS: From a Name to an Answer — visual specification

- **Topic:** DNS name resolution from a client's point of view: the lookup, zones, records, caching, changing records, transport, DNSSEC, split DNS and troubleshooting.
- **Status and version:** 1.1, **locked**. 1.0 was locked by the owner on 2026-10-15; 1.1, approved by the owner the same day, replaces the single split-horizon view with a Split DNS group of two views (10, 11) and adds a VPN fault to diagnosis. Design changes from here need the owner's agreement; copy and accuracy fixes don't. Prototype: [`dns-visual-prototype.html`](dns-visual-prototype.html), generated by `node guide/topics/dns/build-dns-prototype.mjs` from [`dns-lesson.mjs`](dns-lesson.mjs) and [`dns-prototype-client.js`](dns-prototype-client.js). Integrated on 2026-10-15 at `/dns`: canonical source [`src/content/topics/dns.mdx`](../../../src/content/topics/dns.mdx) with content in `src/components/dns/dns-lesson.ts`. The prototype and its `.mjs` files are kept as the 1.0 design record and are not maintained alongside the page; 1.1 was built straight into the page.
- **Target audience:** the brief's audience: developers moving into infrastructure work who use DNS daily but have never followed a lookup end to end.
- **Page promise:** follow one name from your app to the root and back, see every place its answer is cached, move it safely, and tell DNS failures apart with `dig`.
- **Persistent scenario:** `shop.example.com`, `A 192.0.2.10`, TTL 3600, later moving to `203.0.113.20`. Its zone `example.com` is served by `ns1/ns2.example.com` (glue `192.0.2.53`, `198.51.100.53`). All names and addresses are documentation ranges (RFC 2606, 5737, 3849).
- **Format:** Deep Dive, foundational, collection Foundations, slug `dns`.
- **Scope:** Linux clients, recursive resolvers, authoritative zones as seen from outside, 14 record types, caching and negative caching, record changes, UDP/TCP/EDNS/DoT/DoH, DNSSEC validation, split DNS: split-horizon views (Route 53 private zones, BIND views) and split routing (systemd-resolved routing domains, Route 53 Resolver rules and endpoints, CoreDNS forwarding), troubleshooting with `dig` and `resolvectl`.
- **Non-goals:** running authoritative servers, zone transfers, dynamic updates, anycast design, DNS attacks and tunnelling, registrar operations, DoQ, Windows and macOS resolver internals. Kubernetes DNS detail stays in [`/kubernetes-dns`](../../../src/content/topics/kubernetes-dns.mdx); the page lists it under related visuals.

## Visual thesis

**One lookup, followed outward.** The picture grows from browser → resolver → server (view 1), adds the local layers (2), the tree (3–4), then reuses the same actors for caches, change, transport, trust, views and failure. Actors keep their shape and colour everywhere.

## Semantic colour and diagram grammar

Shapes and connector styles come from `LessonDiagram` and `lesson-console.css`. The legend is DNS-specific.

| Element | Form | Meaning |
| --- | --- | --- |
| Grey box (`code`) | your machine: browser, app, laptop, `dig` | where the question starts |
| Teal box (`tool`) | resolver | does the walking and caching |
| Blue box (`kube`) | authoritative server or key | holds the zone's own data |
| Box with a shelf (`store`) | cache | holds copies with a TTL |
| Small box (`part`) | file, record or name | data, not a server |
| Amber dashed box (`person`) | trust anchor | configured trust |
| Solid cyan arrow with a moving dot | happening now | a query or answer in flight |
| Dashed amber arrow with ✕ | no such path | something people assume happens |
| Red arrow or box with ✕ | fails | refused, timed out, withheld |
| Dashed frame | zone or VPC | scope of authority |
| Badge on a box | a state: `referral`, `aa`, `NXDOMAIN`, `hit` | what that actor just did |

Record map districts use tone only as a grouping aid; every sign carries its type and a short label.

## Console structure

- **Index groups:** Finding a name (1–4), The zone's records (5), Time and change (6–7), Transport and trust (8–9), Split DNS (10–11), Context and failure (12–13). One open group; counter `NN / 13`.
- **Toolbar:** active view label and the scenario ribbon `shop.example.com · A 192.0.2.10 · TTL 3600 → moving to 203.0.113.20`.
- **Canvas:** view heading, lede, controls, frames (diagram plus side panels), view-level table.
- **Inspector:** heading, body, three facts, one command, a "worth knowing" note, sources.
- **Bottom:** the point to keep, sources and scope, related visuals (Kubernetes DNS, Networking, HTTP Status Codes, VPC Packet Flow), footer. Previous and next arrows step through views.
- **Fragments:** `#name`, `#before-dns`, `#lookup`, `#zones`, `#records`, `#record-<type>` (opens view 5 with that record), `#caches`, `#change`, `#transport`, `#dnssec`, `#split`, `#routes`, `#diagnose`, `#operate`, `#dns-sources`. Selecting a view or record pushes history; Back and Forward restore it. There are no older anchors to alias.
- **Default:** view 1, step 1.
- **No JavaScript:** every view stacks in order inside the console with all its frames, both change tables, every diagnose check and verdict, all 14 record panels, inspector text and the point to keep.

## Visual contracts

Copy for every frame, inspector, note and takeaway lives in `dns-lesson.mjs`, which is the source for both the prototype and the integration. The contracts below record what each view must show and why; they don't repeat that copy.

### Visual 1 — A browser can't connect to a name

- **Purpose:** establish that DNS is a question with a name and a type, answered by records with a TTL, and that it ends before the connection.
- **Scenario state:** nothing cached. The browser has only the name.
- **Composition:** browser left, resolver top centre, shop server bottom right. Step 1 shows only browser and server with a dashed "connect to a name?" arrow. Step 2 adds the resolver, the question and answer arrows, and a state panel (name, type, answer, TTL). Step 3 draws the real connection to `192.0.2.10` with a "connected" badge.
- **Failure or edge:** the note says DNS doesn't check health; a correct answer can point at a dead server.
- **Accuracy:** "a resolver" is deliberately vague here. View 2 splits it into layers, view 3 into stub and recursive.
- **Sources:** RFC 1034, RFC 1035.
- **Acceptance:** no DNS term other than "record" and "TTL" appears before view 2.

### Visual 2 — Your machine answers itself first

- **Purpose:** separate what `dig` does from what an application does.
- **Composition:** five boxes left to right, numbered edges 1–4: app (`getaddrinfo()`), app's cache, `/etc/hosts`, OS cache, resolver. `dig` sits below the app with its own arrow straight to the resolver, labelled "dig skips 1, 2 and 3".
- **Choices:** the usual path (all hot; code panel compares `getent`, `resolvectl`, `dig`); a hosts entry (stops at 2, badge `10.0.0.5`, warn notice, real-format terminal output); an answer kept too long (JVM cache badge shows the old address while the resolver has the new one).
- **Accuracy:** the order is the common `hosts: files dns`; it comes from `/etc/nsswitch.conf` and varies (systemd-resolved setups put `resolve` first and read `/etc/hosts` themselves). glibc doesn't cache answers. macOS, Windows and browser DoH are mentioned, not drawn.
- **Sources:** nsswitch.conf(5), getaddrinfo(3), resolv.conf(5), systemd-resolved, Java networking properties.
- **Acceptance:** a reader can say why `dig` and `curl` disagree in the hosts-file case, and which command reproduces the app's view (`getent ahosts`).

### Visual 3 — Follow a lookup (hero 1)

- **Purpose:** the central lifecycle: referrals, glue, the authoritative answer, caching, and a warm-cache repeat.
- **Composition:** laptop (stub) left; a tall resolver column centre with its cache below; root, com and example.com servers stacked on the right. Each pair has a query lane above and a response lane below.
- **Steps:** ask → ask the root (minimised, notice about RFC 9156) → referral (real excerpt from `a.root-servers.net`) → ask com → referral with glue (excerpt, glue lines highlighted) → ask example.com → answer with `aa` → cache (three rows with TTLs) → reply (`qr rd ra`, no `aa`) → a second laptop 20 minutes later (cache hit, TTL 2400).
- **Controls:** Next, Back, Restart, "Step N of 10". The live region announces each step's action and caption.
- **Accuracy:** referral excerpts were taken from real `dig +norecurse` queries to `a.root-servers.net` and `a.gtld-servers.net` on 2026-10-15, with names replaced by the scenario's. TLD delegation TTL 172800 is real. Root: 13 identities, many anycast instances. Minimised query type is shown as "who serves com?" rather than a specific QTYPE because resolvers differ (RFC 9156 §3).
- **Reduced motion:** the moving dot is removed; the cyan path and badges carry the step.
- **Acceptance:** after the last step, the cache panel holds three entries with different TTLs, and the reader can explain why the second lookup contacts no server.

### Visual 4 — The tree is cut into zones

- **Purpose:** zones versus names, delegation, glue, and the parent's authority.
- **Composition:** root zone frame top; com and net below; example.com zone frame (with shop, www, ns1 as names inside) and a separate eu.example.com zone frame, joined by an NS edge drawn under both.
- **Choices:** zones and cuts (table: who answers for what); glue (table of what the com zone holds, glue row highlighted); parent still points at the old provider (old-dns node, red edge, `REFUSED` badge, `never asked` on the real zone, stop notice).
- **Sources:** RFC 1034 §4.2, RFC 9471, RFC 2181 §6, RFC 9499.
- **Acceptance:** the lame-delegation frame makes clear that the new servers are healthy and the parent is wrong.

### Visual 5 — Record map

- **Purpose:** a compact, interactive reference for 14 types, in the HTTP status city-map pattern.
- **Composition:** inline SVG, 830 × 442. A dashed frame for the example.com zone holds six districts: Where to connect (A, AAAA, CNAME, HTTPS), Mail and policy text (MX, TXT), Running the zone (NS, SOA), Services (SRV), Certificates (CAA), Proof (DS, DNSKEY, RRSIG). A separate frame, "another zone", holds Reverse zone (PTR). Each sign is an SVG link with the type and a short label. DS reads "fingerprint, in com".
- **Detail panel, below the map:** district, type and phrase, the gloss in quotation marks, the zone-file line, field tiles (name, value, meaning), an "Ask for it" code block, "The trap", and sources.
- **Interaction:** selecting a sign marks it (filled corner, thick border), shows its panel, pushes `#record-<type>` and announces the gloss. Below 761 px a row of type buttons appears under the map, because the map scrolls sideways there. Default: A.
- **Traps chosen:** A (not health-checked), AAAA (stale AAAA breaks only IPv6 users; Happy Eyeballs), CNAME (no other data at the name, so not at the apex; ALIAS/flattening), HTTPS (hints don't replace A/AAAA; alias mode at the apex), MX (target must be a host name, not a CNAME or IP; null MX), TXT (one SPF record; 10-lookup limit), SRV (used only when the protocol says so), NS (parent copy is what resolvers follow), SOA (minimum is the negative-cache TTL), CAA (CA-only, issuance-time, tree climbing), DS (registrar; mismatch means SERVFAIL), DNSKEY (key tag must match DS), RRSIG (signatures expire), PTR (owned by the address holder).
- **Accessibility:** the SVG has a title and a description listing every district and type. Signs are focusable links with names like "MX, mail exchanger". Not checked yet: sign label text is 10.5 px at 1440 px.
- **Acceptance:** `#record-mx` opens view 5 with MX selected; without JavaScript, all 14 panels follow the map.

### Visual 6 — Every layer keeps a copy

- **Purpose:** TTLs count down per copy, negative caching, resolver limits, serve-stale, and caches that ignore TTLs.
- **Composition:** app cache, OS cache, resolver cache, authoritative server, with answers flowing right to left; TTL badges on each.
- **Choices:** a normal answer (3600 → 2400 → 2390; app "30 s, its own rule"); "no such name" (NXDOMAIN cached 300 s; SOA excerpt); the resolver's own limits (604800 kept as 86400); serving stale (authoritative unreachable, expired answer served).
- **View table:** caches that don't follow DNS TTLs: OpenJDK, nginx `proxy_pass` with a fixed host name, connection pools and keep-alive, browsers.
- **Accuracy:** OpenJDK's default without a security manager is implementation-specific (30 s in OpenJDK), and forever with one, per Oracle's networking properties page. Unbound: `cache-max-ttl` 86400, `cache-max-negative-ttl` 3600, `cache-min-ttl` 0 (read 2026-10-15). Serve-stale is optional (RFC 8767).
- **Acceptance:** the reader can name the negative-cache TTL source (the lower of the SOA's TTL and its minimum field) and at least one cache that ignores TTLs.

### Visual 7 — Moving the shop (hero 2)

- **Purpose:** the change-safety mechanism, and why some clients keep the old address regardless.
- **Composition:** plan toggle (Lower the TTL first / Change it now); Next, Back, Restart; a six-moment clock (T − 48 h, T − 47 h, T, T + 2 min, T + 1 h, T + 1 day); the moment's sentence; TTL published and old-server status; four client cards (Laptop, Office resolver, Java service with `networkaddress.cache.ttl=-1`, Pooled connection). Each card shows a state (old address amber, new address green, broken red) plus a value. Under the board, the active plan's full table with future columns blanked.
- **Data:** `change` in `dns-lesson.mjs`. With the TTL lowered, honest caches move within 60 s of T; changing it now leaves them on the old address for up to an hour. In both plans the Java service breaks when the old server goes off, and the pooled connection reconnects to the new address.
- **Accessibility:** clock buttons jump to a moment; the live region reads every client's state after each change. Cards use a text state as well as colour.
- **No JavaScript:** both plan tables, every moment, stacked.
- **Accuracy:** a simplified model. Real resolvers may cap TTLs, serve stale or prefetch, and the exact second each cache took its copy varies.
- **Acceptance:** stepping to T + 2 min shows different results for the two plans; T + 1 day shows the Java service broken under both.

### Visual 8 — How the question travels

- **Choices:** small answer (UDP both hops); large answer (TC=1, then TCP; dig's "Truncated, retrying in TCP mode."); TCP blocked (red response, stop notice citing RFC 7766); encrypted to the resolver (DoT 853 / DoH 443 on the first hop only; badge "sees every query").
- **Accuracy:** 512-byte classic limit (RFC 1035), EDNS (RFC 6891), 1232 bytes from DNS Flag Day 2020.
- **Acceptance:** the encrypted frame makes clear the resolver-to-authoritative hop is unchanged.

### Visual 9 — DNSSEC: a chain of signatures

- **Composition:** three zone frames stacked; trust anchor → root DNSKEY → DS for com → com DNSKEY → DS for example.com → example.com DNSKEY → RRSIG → shop A. Edges alternate "signs" and "fingerprint of" and turn at each zone, so every hop is visible.
- **Choices:** valid chain (`ad` flag); broken link (red from DS for example.com to its DNSKEY; SERVFAIL with real EDE 9 text, `+cd` returns the answer); unsigned zone (chain stops at com, answer marked insecure).
- **View table:** DNSSEC versus DoT/DoH versus CAA.
- **Accuracy:** the EDE line was taken from a real SERVFAIL against `dnssec-failed.org` on 2026-10-15. Compact denial (RFC 9824) is noted because example.com itself answered a nonexistent name with NOERROR during research.
- **Acceptance:** the broken-link frame shows that validating resolvers fail while non-validating ones answer.

### Visual 10 — Same name, different answer

- **Composition:** three rows, each asker → resolver → zone: a laptop on the internet (public resolver, public zone `shop → 192.0.2.10`); an EC2 instance inside a VPC frame (VPC resolver `10.0.0.2`, private zone `shop → 10.0.1.10`); an office PC inside an office frame (office DNS server running BIND with two views, internal view `shop → 10.0.1.10`).
- **Choices:** from the internet; inside the VPC (split-horizon, AWS's "split-view"); name missing from the private zone (`status.example.com`, NXDOMAIN, dashed "falls back?" arrow with ✕, stop notice with the fix); without a cloud (BIND `view` blocks with `match-clients`, first matching view answers); which view answered (`dig @10.0.0.2` and `dig @1.1.1.1` side by side, with an EC2 → public resolver edge).
- **Accuracy:** Route 53's split-view and no-fallback behaviour are from its private hosted zone considerations page; BIND's view matching from the BIND 9 reference (both read 2026-10-15). VPC resolver at the VPC CIDR base + 2.
- **Acceptance:** the no-fallback frame names the documented behaviour, not a guess; the Pod's search path is not in this view.

### Visual 11 — Which resolver gets the question (hero 4)

- **Purpose:** split routing: the client or resolver chooses which server hears each name, by longest matching suffix.
- **Scenario:** `example.com` has public and private views as in view 10; `corp.example.com` lives only on the corporate DNS server `10.20.0.53` (`db → 10.20.0.5`), reachable over a WireGuard-style VPN (`wg0`) and from the VPC through a Route 53 Resolver outbound endpoint and forwarding rule. The corporate server forwards `example.com` to an inbound endpoint (`10.0.0.10`).
- **Composition:** setup buttons; the setup's one-line summary; a table with five places as rows (laptop without VPN, laptop on the VPN, EC2 instance, Pod, on-premises server) and three names as columns (`shop`, `status`, `db.corp`), each cell giving the kind of answer (public view blue, private view purple, corporate teal, not found red), the answer and its last hop; under it, the selected question: hop chips with arrows, the answer, why it went that way, and a "Check it" block in the place's own tool (`resolvectl query`, `dig @10.0.0.2`, `kubectl exec … getent hosts`, `dig @10.20.0.53`).
- **Setups:** as designed; VPN DNS not registered (laptop on VPN: `db.corp` NXDOMAIN via `wlan0`); VPN takes all DNS with `~.` (laptop on VPN: `shop` becomes the private view, `status` disappears); forwarding rule not associated (EC2 and Pod: `db.corp` NXDOMAIN through the Internet Resolver rule); no forwarder on-premises (on-premises: `shop` public, `status` resolves). Cells a setup changes get an amber edge; picking a setup selects its first changed cell.
- **Interaction:** cells become buttons (`aria-pressed`); the live region reads the place, name, hops, answer and reason. Default: laptop on the VPN asking for `db.corp.example.com`, as designed.
- **No JavaScript:** the as-designed table, then a list of what each mistake changes.
- **Accuracy:** systemd-resolved routing (best routing domain by label count, else default-route links; `~.`; a link with a routing-only domain other than `~.` stops being a default route; first successful answer across links) from systemd-resolved.service(8) and systemd.network(5). Route 53: most specific rule wins, forwarding rule beats a private zone of the same name, system rules carve subdomains out, Internet Resolver rule for the rest, inbound and outbound endpoints. CoreDNS answers the cluster domain and forwards the rest to the node's resolvers (Kubernetes "Customizing DNS Service"). All read 2026-10-15. The laptop cases, the VPC and corporate forwarding, and the no-fallback gap are replayed in a Docker lab by `scripts/verify-dns-split.mjs`; `resolvectl` output formats come from that lab (systemd 255). The lab's CoreDNS stands in for Route 53 and passes upstream flags through, so the page shows only status and answer lines from it, never flags.
- **Acceptance:** every setup other than "As designed" changes at least one cell, and each changed cell's reason names the missing or extra piece.

### Visual 12 — Diagnose a failed lookup (hero 3)

- **Composition:** a failure map (app, `/etc/hosts`, resolver, com server, your zone's server, the old provider), the app's error in a red box, numbered checks with command, output and meaning, and a verdict.
- **Faults:** no such name (NXDOMAIN, confirmed `aa` at the source); name exists, type doesn't (NODATA); broken signatures (SERVFAIL + EDE 9 → `+cd` works → DS and DNSKEY tags differ); lame delegation (`+trace` shows the old NS → REFUSED there → new servers fine); no response (`timed out` → another resolver works → check the resolver and firewall); VPN up, internal name fails (`resolvectl query` says not found → `resolvectl status wg0` shows no DNS server → `dig @10.20.0.53` works); works in dig, not the app (`dig` → `getent` → `/etc/hosts`).
- **Interaction:** fault buttons; inside a fault, "Run check N →" reveals the next check, and the verdict appears after the last; "Start over" resets. Switching fault resets its checks. The live region reads each check's command and meaning.
- **Accuracy:** glibc's 5-second per-server timeout and two attempts (resolv.conf(5)). glibc reports SERVFAIL and timeouts as `EAI_AGAIN`. Error strings for curl and Node are their real formats. dig's `communications error … timed out` matches BIND 9.20 output.
- **Acceptance:** each fault's first check already shows a different status line; no two faults share a verdict.

### Visual 13 — A loop for every DNS change

- **Composition:** six-step loop: lower the TTL → change one record → check the source (`dig @ns1 +norecurse`) → watch from outside → drain the old target → raise the TTL. Four steps highlight pairs of edges; a code panel loops over every NS. A table lists continuous signals: SERVFAIL and timeout rate, registrar NS matching zone NS, RRSIG expiry and DS key tags, lookup latency.
- **Acceptance:** this is the production-practice ending the generator requires.

## Implementation

- `src/content/topics/dns.mdx` renders `DnsConsole.astro`, which passes `dnsLesson` to the shared `LessonConsole` with `RecordMap.astro` in slot `view-records`, `ChangeBoard.astro` in slot `view-change` and `RouteBoard.astro` in slot `view-routes`. `dns-client.ts` drives record selection, the change board and the routing board; `src/styles/dns.css` styles all three.
- To change the routing board, edit `splitRouting` in `dns-lesson.ts`: `routes` holds each place's three routes as designed, and each setup lists only the routes it replaces.
- Shared changes, all backward compatible with the AI lessons:
  - `lesson-types.ts`: `Lesson.collection` and `Lesson.legend`, the `custom` view mode with `hero` and a view-level `table`, and `checks` with `verdict` on a frame.
  - `LessonConsole.astro`: renders all of these, and adds a `<id>-console` class to the frame.
  - `lesson-client.ts`: reveals checks one at a time and opens the containing view for a fragment inside it, such as `#record-mx`.
  - `lesson-console.css`: checks panel and legend swatches for the tool, store, part and person kinds.
- To change a record type, edit `records` in `dns-lesson.ts`; its sign is placed in its district's row.
- `node scripts/verify-dns-lesson.mjs` replays eight claims against live servers with dig: root and com referrals, rd/ra without aa, NXDOMAIN with SOA, SERVFAIL with an extended error, `+cd`, the ad flag, and TC with a TCP retry.
