01 / FINDING A NAME

A browser can't connect to a name

You type shop.example.com. Before a single byte of the shop can load, something has to turn that name into an address.

Step 1 of 3
INSPECTOR

DNS answers one kind of question

Every lookup is a name plus a type, and every answer is a set of records of that type. A, AAAA, MX and the rest are just different questions about the same name. The TTL tells anyone holding the answer how long they may reuse it without asking again.

WORTH KNOWING

DNS doesn't check that the server behind an address is healthy. A perfectly correct answer can point at a machine that is down.

02 / FINDING A NAME

Your machine answers itself first

Most applications don't speak DNS. They ask the operating system, and the operating system checks a few places before any packet leaves.

INSPECTOR

dig is not what your app does

dig, host and nslookup send a DNS query straight to a resolver. Your application goes through the system resolver library, which reads /etc/hosts and may use a local cache, and the app may cache on top of that. When dig and the app disagree, the difference is somewhere between them.

does not cache answers

WORTH KNOWING

macOS and Windows have their own system resolvers and caches, and browsers can send DNS over HTTPS to a provider they choose, skipping the system resolver entirely.

03 / FINDING A NAME · INTERACTIVE

The resolver walks the tree for you

Your laptop asks one question. A recursive resolver does the walking: root, then com, then the servers for example.com, keeping everything it learns.

Step 1 of 10
INSPECTOR

Referrals, then an answer

Only the last server knows the answer. The root and com servers know who to ask next, and say so with NS records in a referral. Because the resolver caches those referrals for days, the full walk is rare: most lookups start at a server the resolver already knows.

04 / FINDING A NAME

The tree is cut into zones

The referrals in the last view happen at zone cuts. A zone is the part of the tree one set of servers answers for; the parent points to it with NS records.

INSPECTOR

Authority is handed down

A parent zone doesn't store its children's records. It stores NS records that say who does, plus glue when needed. That one handover is what lets each organisation run its own part of the tree.

A subdomain is not automatically a separate zone. eu.example.com becomes one only when example.com delegates it with NS records.

06 / TIME AND CHANGE

Every layer keeps a copy

The answer you saw in the lookup doesn't live in one cache. It's copied into the resolver, the operating system and sometimes the app, each counting down on its own.

Caches that don't follow DNS TTLs
WhereWhat it does
OpenJDKCaches successful lookups for 30 s by default, forever if a security manager is installed; set networkaddress.cache.ttl in java.security.
nginx proxy_pass with a fixed host nameLooks the name up when the configuration loads. A variable plus a resolver directive makes it look up at run time.
Connection pools, keep-alive, HTTP/2Don't look anything up while the connection is open. They keep using the old address until it closes.
BrowsersKeep their own short-lived cache in addition to the OS.
INSPECTOR

A TTL is a maximum, counted per copy

A cache may drop an answer early, and well-behaved caches never keep it past its TTL. But the clock starts when each copy is made, resolvers bound TTLs with their own limits, and some application caches ignore DNS TTLs altogether.

08 / TRANSPORT AND TRUST

How the question travels

Most lookups are one UDP packet each way. Large answers need TCP, and the hop from your laptop to the resolver can be encrypted.

INSPECTOR

Size decides UDP or TCP

Classic DNS limited UDP answers to 512 bytes. EDNS lets each side advertise a bigger buffer, and DNS Flag Day 2020 settled on 1232 bytes to avoid IP fragmentation. Anything larger falls back to TCP, so TCP 53 has to work.

Plain DNS
UDP and TCP 53
DNS over TLS
TCP 853
DNS over HTTPS
443, alongside web traffic
FORCE TCPdig +tcp shop.example.com
WORTH KNOWING

Encrypting the hop doesn't prove the answer is genuine; a resolver can still pass on a forged record. Proving answers is DNSSEC's job, next.

RFC 1035: DNS implementation ↗RFC 6891: EDNS(0) ↗RFC 7766: DNS over TCP ↗DNS Flag Day 2020: 1232-byte buffer ↗RFC 7858: DNS over TLS ↗RFC 8484: DNS over HTTPS ↗

THE POINT TO KEEPDNS needs both UDP and TCP on port 53; encryption protects one hop from eavesdroppers, not the answer's authenticity.

11 / CONTEXT AND FAILURE · INTERACTIVE

Diagnose a failed lookup

Applications flatten every DNS problem into "could not resolve". Pick a fault, then run the checks in order to see the evidence that separates them.

INSPECTOR

Read the status, then ask the source

Start with the status and flags, not the application's message. NXDOMAIN and NODATA are answers from the zone. SERVFAIL means a resolver couldn't produce a trustworthy answer. A timeout means nobody answered. Then ask the authoritative server directly with +norecurse to take caches out of the picture.

WORTH KNOWING

Application errors don't keep these distinctions. glibc reports SERVFAIL and timeouts as EAI_AGAIN, a temporary failure that callers often retry.
